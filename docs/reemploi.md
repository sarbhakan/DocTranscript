# Veille GitHub et stratégie de réemploi

Veille documentaire au 13 novembre 2026. Les fonctionnalités sont celles décrites par les mainteneurs ; aucune n’a été vérifiée en exécutant ces applications. Les licences indiquées pour le code ne couvrent pas nécessairement les modèles, données, graphismes et dépendances.

| Projet | Réemploi envisagé | Pourquoi garder une frontière |
| --- | --- | --- |
| [Scribe](https://github.com/ChrisMcKee1/scribe), [licence MIT](https://github.com/ChrisMcKee1/scribe/blob/main/LICENSE) | Référence la plus proche pour l’architecture Windows : WPF/.NET, NAudio, Parakeet sur sherpa-onnx, raccourci et saisie. | [Handy](https://github.com/cjpais/Handy), [licence MIT](https://github.com/cjpais/Handy/blob/main/LICENSE), [versions](https://github.com/cjpais/Handy/releases) | Comparer l’ergonomie du raccourci et la gestion des modèles. Ses chiffres ne se comparent pas à ceux de NoteVive sans essai contrôlé sur des dictées fictives identiques. |

**Stratégie proposée :** partir d’un petit éditeur Windows et d’un moteur réutilisé, derrière un contrat permettant d’en changer. Favoriser un seul runtime si sherpa-onnx couvre le modèle français à flux natif, la transcription finale et le contexte lexical requis sur les postes cibles. Un second runtime ou une seconde passe n’entre dans la distribution que si le gain mesuré justifie le coût en mémoire, tests et maintenance. Le cahier de veille des [moteurs](veille-moteurs.md) et celui de la [qualité médicale](qualite-medicale.md) détaillent les candidats et les droits à vérifier. Le choix se fait sur les preuves, la maintenance et les licences plutôt que sur les étoiles seules.

Avant de reprendre un composant : identifier version, commit, licence et dépendances transitives, contrôler binaires et téléchargements implicites, conserver les mentions requises, consigner ce qui est copié et ce qui est seulement observé. Épingler aussi la révision, la licence et le SHA-256 de chaque poids et lexique. Pour un dépôt public, documenter la licence du projet avant publication ; tant qu’elle n’est pas choisie, aucun droit de redistribution du projet n’est supposé.

## Dev Toolkit Orchestrator

Le plugin a servi à répartir la veille et à sélectionner des références ; aucun de ses dépôts n’a été installé ni exécuté. Aucun fichier d’inventaire d’installation n’est requis tant que rien n’a été installé. Les pages consultées sont des références amont, pas des versions intégrées au produit. Le prochain lot fige une version uniquement pour ce qui entre effectivement dans le banc.

| Module du plugin | Utilité vérifiée et disposition |
| --- | --- |
| [ponytail](https://github.com/DietrichGebert/ponytail) | Consignes de simplicité pour agents de développement ; utiles comme principe de cadrage : prouver un moteur avant de multiplier les couches. Aucun code requis. |
| [i-have-adhd](https://github.com/ayghri/i-have-adhd) | Consignes de présentation pour rendre les décisions et prochaines actions visibles. Le registre de suivi suffit pour ce lot ; aucune dépendance. |
| [ui-ux-pro-max-skill](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) | Référence de conception pour P1, notamment contraste et accessibilité ; la recette WPF, clavier et Narrateur restent les preuves attendues. |
| [browser-use](https://github.com/browser-use/browser-use) | Automatisation de navigation. Éventuellement utile sur une page de test locale et fictive ; ne remplace pas les tests de focus ni de saisie Windows. Pas d’activation. |
| [humanizer](https://github.com/blader/humanizer), [rea](https://github.com/morluto/rea) | Relecture rédactionnelle et rétro-ingénierie respectivement. Aucune raison de les installer pour ce cadrage ; l’interopérabilité repose sur les API et comportements documentés. |
